## Isolated algorithm and termination cohorts

`matrix-register SPEC.json` expands a pinned base campaign and explicitly declared studies into separate v2 configurations. Algorithm treatments preserve move families, weights, selected-count limits, termination, instrumentation and resource declarations; acceptor size and accepted-count forager settings remain explicit because they differ by algorithm. A neighborhood treatment adds exactly one family while retaining existing order/weights and its fixed acceptance package. A termination treatment retains its enclosing spent and existing step caps. Interactions require a separate registration.

`matrix-run REGISTERED_DIRECTORY` checks all configuration bytes and toolkit hashes before one serial dispatch. It records the registration hash, campaign archive pointers, terminal state and completed campaigns. A failed/interrupted campaign stops that registration, with its original failure retained. Repeating the command rejects an already-dispatched registration. A separately registered different cohort is independent work, never a retry of the failed observation. The usual TCP 47983 measurement lock remains in force.

`matrix-analyze REGISTERED_DIRECTORY` verifies the original specification, dispatched registration, original configuration bytes, manifest pointers and archived toolkit. It independently revalidates sealed cases and writes a new analysis with current analyzer hashes. It never dispatches or rewrites old measurements. All five measured registrations pass this reanalysis under the final analyzer.

Every adjustable parameter remains in JSON. CLI arguments select artifacts only. Original specification bytes, resolved configurations, exact source/JAR/JDK identities, per-case native XML/reports and receipts remain in immutable local archives outside build-clean directories.

The final study set separates reference, shared-target fairness, repair, complete-policy and one-neighborhood cohorts. It uses explicitly declared synthetic short-budget inputs and 200 ms fresh-JVM warmup. The latter remains uncalibrated, so even a favorable numeric comparison cannot select a performance winner. Repair retains unresolved demand and explicitly unavailable independently validated intermediate time-to-feasibility; it is excluded from feasible cost ranking. Native failures, incomplete proposals and cooperative overshoot remain outcomes rather than proof of infeasibility.

No SA temperature study, Enterprise feature, custom parallel scoring or solver fork is introduced. A Timefold booking prototype lacks a booking profiling hypothesis; declarative timing shadows lack isolated dominant timing and route-length evidence. Both receive prerequisite-not-met dispositions. Longer-budget sensitivity and production-budget termination ranking await stable path calibration.

LA passes the registered reference cost/fairness screen in this short-budget two-dataset cohort. The analysis preserves that favorable result, but uncalibrated execution and absent untouched production confirmation prevent selecting a finalist. Early-stop comparisons and native cooperative overshoot are retained without declaring a termination policy superior. The repair control's `scoringMatchesValidation=false` accompanies independently infeasible work; it is not an unexplained invalid accepted result. The bounded search does not prove that the repair is impossible.

The compatibility gate also exercises twelve algorithm/termination/scope combinations under FULL_ASSERT, with explicit enclosing spent and step caps. These tiny fixtures and the synthetic measurements have different roles and are not pooled.

## Finalist, held-out confirmation and resource gates

There is no qualified tuning finalist to freeze. Do not use the same datasets for tuning and confirmation, choose a winner from unstable runs, or describe existing HTTP fixtures as a matched service capacity study. Held-out production-budget policy confirmation, matched embedded/remote p50/p95/resource studies, independent metro/day scaling, provider thread-safety/single-flight/cancellation checks and dense/sparse encoding performance selection remain blocked prerequisites for promotion.

`promotion-review SPEC.json` reads a hash-pinned confirmation receipt and returns each failed gate. It checks unchanged finalist configuration, disjoint dataset identities, explicit 20-second operation/15-second search allowances, stable calibration, matching load/resources/served identities, all requested outcomes, no invalid accepted result or added adverse outcomes/overtime, useful outcomes, exact 5% p95 boundary, strict negative cost upper interval and no scenario-family cost/fairness reversal. Tiny decimal fairness regressions and latency boundary excess remain distinguishable. Null, nonfinite, missing and unknown values fail instead of becoming fabricated measurements.

This tool verifies the supplied receipt's arithmetic and identities. It does not independently certify experimental provenance; reviewers must inspect its pinned raw source archives, load/cache cohorts, intended/actual arrivals, serialization, queueing, memory, throughput and cleanup. Its output never authorizes deployment. Synthetic evidence remains synthetic even if other arithmetic gates pass. The confirmation receipt is not generated from this delivery's short fixtures.

7. Old historical reports remain readable. Incompatible policy/cost/score/dataset versions require fresh unapplied previews and booking offers. A hash, score, migration receipt or review-tool result never authorizes application.

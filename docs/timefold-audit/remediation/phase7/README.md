## Attempt ownership and retries

The caller stores `daily_calculation_attempt`: request key, SHA-256 fingerprint of the canonical operation and explicit request inputs, unique owner token, state, database expiry, captured scheduling/routing identities, result run reference, immutable response JSON and failure reason. SQL constraints reject missing ownership, malformed fingerprints, inconsistent terminal results and missing failure reasons. Required saved response fields, summaries and optional outcome/solver/policy analysis are validated before reuse.

The operation clock starts before claiming and capacity acquisition. Claim transactions serialize a request key with a PostgreSQL advisory transaction lock and commit before the background queue. Identical completed keys return the saved response without routing, solving or admission. Conflicting input fingerprints return conflict. An active key never transfers ownership to a second caller. Failed, cancelled, stale and abandoned keys remain terminal; a new calculation requires an explicit new request key. Calls without a key generate a fresh attempt, so clients must supply a stable key for transport retries. Repair has an overload accepting a key, including technician and interval bounds in its fingerprint; existing callers without a key represent fresh business invocations.

Expired claimed attempts are reconciled to `ABANDONED` when their key is next inspected. There is no lease stealing, automatic rerun or hidden fallback. Expiry is established using the database clock plus the original operation's remaining allowance. Pre-solve binding, completion and the final commit guard require the same owner and an unexpired attempt. This phase does not add an eager background reconciler. Failed cleanup leaves the claim and its expiry inspectable, with a warning; subsequent inspection can mark abandonment.

Legacy completed `optimization_run.requestKey` rows are imported on first compatible daily reuse. The import owner and expiry describe that import only, never a historical solver execution. Results without a run, such as repair `NO_SHIFT`, are retained in response JSON with an intentional null run reference. The run reference is logical: explicit fixture or benchmark cleanup may remove a run while its attempt receipt remains. Reusing a receipt never authorizes applying a deleted, stale or incompatible run.

## Database and calculation phases

1. A short `REQUIRES_NEW` claim transaction commits ownership before admission.
2. A short `REQUIRES_NEW`, repeatable-read transaction captures technicians, effective availability, qualifications, approved absences, appointments, promises, locations, endpoints, exact rates, policy and schedule versions. Missing schedule-day version rows are initialized here. Concurrent initialization may fail with a serialization conflict; it is retained as failure and is not automatically retried.
3. Routing runs outside the snapshot transaction with an explicit captured identity. Fresh provider identity and scheduling revisions are checked before calculation. The attempt records that revision before solving. Reference, fairness, repair, independent assessments, assignments, summaries and persistence parameters are prepared outside database transactions.
4. A fresh routing identity observation precedes the final transaction. That short transaction locks scheduling input tables in `SHARE` mode, checks the structured input revision and cutoff, writes the proposal and change rows, prepares the response, and transitions the matching attempt to `SUCCEEDED` atomically. Ownership, expiry, cutoff and request time are checked again immediately before commit.

The structured revision preserves actual nulls and JSON escaping. Appointment, schedule, override, absence interval, reservation and hold rows are scoped to the service day. Referenced booked jobs and addresses, the reservation-obligation view, and global configuration and technician facts are included. This is conservative: changes elsewhere in that day's fleet or global technician/configuration inputs can invalidate a preview even when its metro would be unaffected. It avoids relying on every Java and Prisma writer to increment a newly introduced counter.

The final table lock conflicts with input writers' ordinary PostgreSQL row-exclusive table locks, preventing a write from committing between revalidation and proposal commit. Readers continue. This fence currently spans metros and is held through final response preparation. Routing, Timefold, route reporting and proposal construction do not hold it. Lock waits consume the original request allowance; failures and deadlock victims do not rerun. This is a correctness boundary with unmeasured contention and payload cost, not a latency or throughput claim. Narrowing the fence requires equivalent cross-writer protection and measured evidence.

Provider identity checks are fresh observations, not an atomic lock on an external routing service. The provider validates the explicit expected identity while obtaining legs. Application continues to fetch and independently validate current roads and scheduling facts under its existing locks. A hash, cached score, durable response or successful attempt does not provide apply authority. Concurrent apply still locks the run and schedule versions and independently checks promises, coverage, feasibility, zero overtime, holds and policy.

Cancellation cleanup uses a separate bounded two-second transaction outside the expired request clock. The worker retains its admission lease until cleanup unwinds. Conditional cleanup cannot overwrite a succeeded result after a lost commit acknowledgement. Socket delivery remains outside commit acknowledgement; a repeated key resolves the durable result instead of starting a second solve. Existing deadline receipts remain available.

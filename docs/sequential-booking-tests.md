# Sequential booking and optimization tests

`/dispatch/testing` is a local workload runner. It adds generated requests to the current Omaha schedule through real booking offers and selection, then creates whole-day optimization previews. Staff can review current, before, and proposed road routes and use the same guarded Apply workflow shown in Dispatch.

## Enable locally

Run `docker compose up -d`. Local Compose enables the route by default, forwards the flag to the portal, runs the additive migration, and rebuilds the application images. Open `http://localhost:3001/dispatch/testing`. To opt out, set `LOCAL_BOOKING_TESTS=false` in the root ignored `.env` and recreate the web container. Remove that override or set it to `true` to enable the route again.

The Compose default does not change a host-run portal or production deployment. Those environments remain disabled unless they explicitly set `LOCAL_BOOKING_TESTS=true`. For a host-run portal, also set `DATABASE_URL` and `ENGINE_URL`, apply `npx prisma migrate deploy`, and start Next normally. Use the updated Java scheduler because preview retry keys require the new migration and implementation. The page and APIs require a localhost or loopback host; API requests also reject cross-origin browser calls. Keep the local Compose ports bound to loopback. This is a local test tool, not a staff authentication system.

## Run and review

1. Choose 1-100 requests, an optional unsigned 32-bit seed, service weights, and an offer policy. Defaults are 20 requests, a blank seed, equal weights, and earliest returned offer. A blank seed is resolved with a cryptographically random value and the resolved value is saved. Zero excludes a service. Weights are relative probabilities, not exact quotas.
2. Start a run. The paused draft is saved immediately. The page resumes it and advances address generation in batches of at most 12 candidates. It samples continuous candidate coordinates inside the configured radius of an Omaha depot and reverse-geocodes them with the local Nominatim service. A candidate must have an OSM house number, named road, city or municipality, postal code, finite coordinates inside the service area, and a unique normalized address and coordinate. The persisted state comes from the metro's required `stateCode`; any state returned by Nominatim must match it. This supports bounded PBF extracts that omit the enclosing state relation without inventing address data. The candidate must also have directed self-hosted road routes both to and from at least one active technician qualified for its service. Active appointment addresses and other addresses in the run are excluded.
3. The progress panel reports accepted addresses, requested addresses, candidates examined, completed batches, active elapsed time, and generation status. Progress is persisted after every completed batch. Several empty batches display a warning, but generation has no total attempt or elapsed-time cap. An impossible data set continues searching until Pause or Stop is selected.
4. After every requested address is ready, the runner rechecks active-address collisions and creates the complete request set in one transaction. If an accepted address became active, that candidate is discarded and searching continues. Customer, job, address, and booking records are not created during generation.
5. Each later operation creates or recovers one pending job, requests reserved offers, saves the selected window, and calls `/v1/offers/select`. Selection commits the appointment. The next job begins only after that operation finishes. Earliest means the earliest returned window, not an exhaustive search for the earliest possible date.
6. Pause or Stop finishes the active generation batch, request, or preview. Pause allows Resume; Stop is final. Both retain completed progress, bookings, and history. Closing or navigating away ends browser progression after the current operation. Reopen from history or the `?run=` URL and explicitly Resume. A persisted RUNNING status does not itself start a worker.
7. After all requests have BOOKED or NO_OFFER outcomes, the browser advances through one preview per affected service date. If the page closes after the last booking, Resume finishes previews.
8. Review current, before, and proposed road routes, drive minutes, paid route minutes, overtime, modeled cost, and changed appointments. Previews cover the entire day, including earlier appointments and bookings from other runs. `SKIPPED` is explicitly non-applyable and displays its reason. A current `PREVIEW` can be applied from either the testing page or Dispatch after confirmation. Both entry points call the same endpoint, which rechecks the cutoff, active holds, schedule versions, routing identity, configuration version, feasibility, and cost improvement. A successful apply refreshes saved status and switches the route view to current roads. The comparison link identifies the exact saved run even after it leaves the latest history page.
9. When a run is paused, stopped, or completed, `Delete generated appointments` performs a confirmed run-scoped purge. It removes only jobs whose full `booking-test:<run UUID>:` prefix matches this run, along with their appointments, holds, offers, booking optimization artifacts, outbound events, addresses, and synthetic customers. It resequences surviving active appointments and increments affected schedule-day versions. Manual appointments, other runs, and optimization history remain. Saved before and proposed maps continue to render from each optimization snapshot while the referenced technicians and routing graph remain available. Current roads always reflect the live schedule and can therefore change or become empty after purge. Purge is idempotent and records its timestamp and removed appointment count. It does not reverse changes that an applied optimization made to surviving appointments.

The booking horizon is the next ten weekdays after today in America/Chicago, matching the scheduler. There is no date override. The page shows the current horizon; the run saves its initial horizon and each completed attempt saves its own horizon. A long pause can move subsequent requests into a later horizon.

## Recovery and persistence

The additive `booking_test_run`, `booking_test_generation`, `booking_test_request`, and `booking_test_preview` tables retain configuration, private generation state, accepted inputs, ordered requests, offers, selections, outcomes, durations, attempt history, appointment IDs, and optimization IDs. The generation journal stores the seeded random state, round-robin cursor, and a pending candidate batch before external calls. If a process or HTTP response is lost, Resume retries the same coordinates. Each request uses `booking-test:<run UUID>:<ordinal>` as its job ID, booking retry key, and customer/job external tag. Appointments are associated through their unique job IDs. Creation retries use the same run UUID and reject conflicting settings. Runs created before the generation journal was added are treated as intentionally generation-complete.

`GET /api/dispatch/testing` lists runs; `?id=<UUID>` reads one. POST accepts `{id, action}` with `create` (plus `config`), `resume`, `pause`, `stop`, `purge`, or `advance` (plus the last returned `revision`). Create accepts a null or omitted seed and returns the resolved seed in the saved configuration. Run responses include nullable `purgedAt` and `purgedCount` fields. A PostgreSQL advisory transaction lock permits only one advancing, resuming, or purging operation across local runs. An atomic revision claim prevents replayed advance requests from booking the next job. Control writes remain available while the operation finishes. PostgreSQL releases the lock on connection loss; independently committed journal writes permit recovery without browser memory.

Each address batch uses deterministic candidate ordering for an explicit seed and at most 12 concurrent reverse lookups. There is no overall generation cutoff. Each reverse lookup retains its 8-second timeout, and each routing check retains its 30-second timeout. Nominatim, scheduler, and saved JSON responses are validated before use. Malformed journals pause without creating requests. This project uses OpenStreetMap address and road data and retains the required [OpenStreetMap attribution](https://www.openstreetmap.org/copyright).

Engine calls time out after 45 seconds. Before retrying a job, the runner waits behind the scheduler's job transaction and checks for an existing appointment. Lost selection responses retain their saved choice for idempotent reconciliation. Explicit confirmation conflicts pause and clear only the current choice, preserving it in attempt history; Resume can obtain current offers for the same job. Routing, configuration, and ambiguous network errors pause instead of becoming NO_OFFER results. Only a successful empty offer response counts as no capacity, and that outcome continues the run. Page network failures halt progression without an automatic retry.

Day previews use an optional `request_key` on the existing preview endpoint. PostgreSQL serializes callers with the same key, atomically saves the preview and key, and returns the saved run on retry. Reusing a key for another metro or date conflicts. This prevents duplicate history after a lost response. Customer booking and guarded apply rules are unchanged.

## Interpretation and limitations

- Offer availability is BOOKED divided by BOOKED plus NO_OFFER. Pending and failed requests are excluded. Mean offer count uses completed requests. Current error counts exclude recovered errors; attempt history retains those failures.
- Booking latency totals recorded processing attempts for booked requests. It excludes pauses and cannot recover elapsed time from a process killed before saving its timing journal. Days until service is a Chicago calendar-day difference from initial request processing.
- An explicit seed reproduces candidate order and random-selection fractions. Nominatim data, map data, schedule state, date, database collisions, offer order, and solver execution can change results. Repeated runs add workload and are not identical benchmark snapshots.
- Stop does not undo appointments or release offers from an earlier failed operation. Remaining scheduler reservations expire under the existing ten-minute rule. Use the run-scoped purge after the run reaches an eligible state.
- A preview is a snapshot, not realized savings. Applied status and timestamp come from the actual optimization run separately. Later changes can invalidate a proposal; Dispatch apply retains its validation and cutoff checks. A frozen date still returns a conflict.
- The runner progresses only from an open browser. It is not a background queue or throughput benchmark. Resume may temporarily conflict while an earlier bounded operation finishes. Resolve routing or database outages before retrying.

## Verification

`npm run test:booking-tests` covers optional and deterministic seeds, deterministic batches and saved random state, round-robin fairness, real-address parsing, uniqueness and collision rejection, routability filtering, malformed Nominatim responses, weights, selection policies, horizon boundaries, and access gates. `npm run test:booking-tests:integration` refuses databases other than `waterflex_test` and requires seeded Omaha configuration plus the deterministic routing fixture and Java scheduler. Set `DATABASE_URL` and `ENGINE_URL` explicitly. The integration suite injects fixed fixture addresses because CI does not import Nominatim; production advancement always uses the validated local Nominatim and routability path. It retains tagged test history in that disposable database for inspection.

Integration checks cover draft creation, persisted generation progress, repeated empty batches, pending-batch recovery, malformed generation journals, sequential order, duplicate creation and advances, all-or-nothing request creation, pause/resume/stop, concurrent callers, no-offer continuation, routing failures, confirmation conflicts, process interruption, lost confirmation and preview responses, unchanged promises and assignments before apply, exact-run purge, idempotent purge, survivor resequencing, and preservation of manual appointments, other runs, and optimization history. Browser coverage checks generation progress, history recovery, apply confirmation, stale-preview errors, applied-state refresh, route phase switching, purge confirmation, and purge state. Successful bookings must have a selected scheduler offer set. Existing booking, optimizer/apply, and time-off checks also run in CI. The fixture accepts only fixed Monaco and Omaha sample/home coordinates; it is not a production routing fallback.

For real-road verification, start a small run against the local Omaha graph, inspect saved windows and preview results, reload the run, and follow its Dispatch comparison link. Leave proposals unapplied unless explicitly testing manual approval.

# Sequential booking and optimization tests

`/dispatch/testing` is a local workload runner. It adds generated requests to the current Omaha schedule as customer bookings through the public scheduling API for the client active when the run starts, then asks for each booked day's daily proposal. Staff can review each proposal and its day's current road routes, and apply it with the same guarded workflow shown in Dispatch.

## Enable locally

Run `docker compose up -d`. Local Compose enables the route by default, forwards the flag to the portal, runs the additive migration, and rebuilds the application images. Open `http://localhost:3001/dispatch/testing`. To opt out, set `LOCAL_BOOKING_TESTS=false` in the root ignored `.env` and recreate the web container. Remove that override or set it to `true` to enable the route again.

The Compose default does not change a host-run portal or production deployment. Those environments remain disabled unless they explicitly set `LOCAL_BOOKING_TESTS=true`. For a host-run portal, also set `DATABASE_URL`, `SCHEDULER_API_URL` and the client's `SCHEDULER_API_TOKEN_<CLIENT ID>` (see the README), apply `npx prisma migrate deploy`, and start Next normally. The scheduler must list `metro-omaha` in `ROUTING_METRO_URLS`, and the active client must have a depot in the Omaha metro. The page and APIs require a localhost or loopback host; API requests also reject cross-origin browser calls. Keep the local Compose ports bound to loopback. This is a local test tool, not a staff authentication system.

## Run and review

1. Choose 1-100 requests, a generation radius of 10, 20, 30, 45, or 65 miles, an optional unsigned 32-bit seed, service weights, and an offer policy. Defaults are 20 requests, a 30-mile radius, a blank seed, equal weights, and earliest returned offer. The radius controls only generated test addresses; customer booking coverage remains the metro's configured 65 miles. A blank seed is resolved with a cryptographically random value and the resolved value is saved. Zero excludes a service. Weights are relative probabilities, not exact quotas.
2. Start a run. The paused draft is saved immediately. The page resumes it and advances address generation in batches of at most 12 candidates. It samples continuous candidate coordinates inside the run's saved radius of an Omaha depot and reverse-geocodes them with the local Nominatim service. The create API rejects unsupported presets and radii above the metro's current customer service radius. A candidate must have an OSM house number, named road, city or municipality, postal code, finite coordinates inside the saved run radius, and a unique normalized address and coordinate. The persisted state comes from the metro's required `stateCode`; any state returned by Nominatim must match it. This supports bounded PBF extracts that omit the enclosing state relation without inventing address data. There is no separate road check: a candidate the scheduler cannot reach by road gets no offer when it is booked. Active appointment addresses and other addresses in the run are excluded.
3. The progress panel reports accepted addresses, requested addresses, candidates examined, completed batches, active elapsed time, and generation status. Progress is persisted after every completed batch. Several empty batches display a warning, but generation has no total attempt or elapsed-time cap. An impossible data set continues searching until Pause or Stop is selected.
4. After every requested address is ready, the runner rechecks active-address collisions and creates the complete request set in one transaction. If an accepted address became active, that candidate is discarded and searching continues. Customer, job, address, and booking records are not created during generation.
5. Each later operation creates or recovers one pending job, searches for offers as the customer would, saves the selected window, then selects and confirms its hold through the public API. The confirmed booking is written with a compare-and-set on every technician-day it changes. The next job begins only after that operation finishes. Earliest means the earliest returned window, not an exhaustive search for the earliest possible date.
6. Pause or Stop finishes the active generation batch, request, or preview. Pause allows Resume; Stop is final. Both retain completed progress, bookings, and history. Closing or navigating away ends browser progression after the current operation. Reopen from history or the `?run=` URL and explicitly Resume. A persisted RUNNING status does not itself start a worker.
7. After all requests have BOOKED or NO_OFFER outcomes, the browser advances through one preview per affected service date. If the page closes after the last booking, Resume finishes previews.
8. Review each proposal's decision and reason, modeled cost, proposed timed routes, appointment changes, and unresolved appointments, beside the day's current road routes. Proposals cover the entire day for the run's client, including earlier appointments and bookings from other runs. Only an `OPEN` proposal can be applied, from either the testing page or Dispatch after confirmation; both call the same endpoint, which writes the proposal only if none of its technician-days changed since it was made. Runs saved before the public API show their engine previews as a read-only summary; those cannot be applied.
9. When a run is paused, stopped, or completed, `Delete generated appointments` performs a confirmed run-scoped purge. It removes only jobs whose full `booking-test:<run UUID>:` prefix matches this run, along with their appointments, offers, outbound events, addresses, and synthetic customers. The surviving visits on each open day it touches are re-timed through the public API in the same write; a frozen day keeps its times. Manual appointments, other runs, and proposal history remain, and saved proposals still list the visits they routed. Current roads always reflect the live schedule and can therefore change or become empty after purge. Purge is idempotent and records its timestamp and removed appointment count. It does not reverse changes that an applied proposal made to surviving appointments.

The booking horizon is the next ten weekdays after today in America/Chicago, matching the scheduler. There is no date override. The page shows the current horizon; the run saves its initial horizon and each completed attempt saves its own horizon. A long pause can move subsequent requests into a later horizon.

## Recovery and persistence

The additive `booking_test_run`, `booking_test_generation`, `booking_test_request`, and `booking_test_preview` tables retain configuration, private generation state, accepted inputs, ordered requests, offers, selections, outcomes, durations, attempt history, appointment IDs, proposal IDs, and the client each run books for. The generation journal stores the seeded random state, round-robin cursor, and a pending candidate batch before external calls. If a process or HTTP response is lost, Resume retries the same coordinates. Each request uses `booking-test:<run UUID>:<ordinal>` as its job ID, booking retry key, and customer/job external tag. Appointments are associated through their unique job IDs. Creation retries use the same run UUID and reject conflicting settings. Saved configuration JSON from before radius selection has no `radiusMi`; it is normalized to 65 miles so those runs retain their original generation behavior and remain resumable. Runs created before the generation journal was added are treated as intentionally generation-complete. No database migration is required for radius selection.

`GET /api/dispatch/testing` lists runs; `?id=<UUID>` reads one. POST accepts `{id, action}` with `create` (plus `config`), `resume`, `pause`, `stop`, `purge`, or `advance` (plus the last returned `revision`). Create requires `radiusMi` and accepts a null or omitted seed, then returns the selected radius and resolved seed in the saved configuration. Run responses include nullable `purgedAt` and `purgedCount` fields. A PostgreSQL advisory transaction lock permits only one advancing, resuming, or purging operation across local runs. An atomic revision claim prevents replayed advance requests from booking the next job. Control writes remain available while the operation finishes. PostgreSQL releases the lock on connection loss; independently committed journal writes permit recovery without browser memory.

Each address batch uses deterministic candidate ordering for an explicit seed and at most 12 concurrent reverse lookups. There is no overall generation cutoff. Each reverse lookup retains its 8-second timeout. Nominatim, scheduler, and saved JSON responses are validated before use. Malformed journals pause without creating requests. This project uses OpenStreetMap address and road data and retains the required [OpenStreetMap attribution](https://www.openstreetmap.org/copyright).

Before retrying a job, the runner waits behind the scheduler's job transaction and checks for an existing appointment. Lost selection responses retain their saved choice for idempotent reconciliation. Explicit confirmation conflicts pause and clear only the current choice, preserving it in attempt history; Resume searches again for the same job, which ends its earlier offers. Routing, configuration, and ambiguous network errors pause instead of becoming NO_OFFER results. Only a successful empty offer response counts as no capacity, and that outcome continues the run. Page network failures halt progression without an automatic retry.

Each day's preview is a new daily proposal. A retry after a lost response asks again and saves the newer proposal in place of the lost one, so the run keeps one preview per day; the earlier proposal stays in the client's proposal history. Customer booking and guarded apply rules are unchanged.

## Interpretation and limitations

- Offer availability is BOOKED divided by BOOKED plus NO_OFFER. Pending and failed requests are excluded. Mean offer count uses completed requests. Current error counts exclude recovered errors; attempt history retains those failures.
- Booking latency totals recorded processing attempts for booked requests. It excludes pauses and cannot recover elapsed time from a process killed before saving its timing journal. Days until service is a Chicago calendar-day difference from initial request processing.
- An explicit seed reproduces candidate order and random-selection fractions. Nominatim data, map data, schedule state, date, database collisions, offer order, and solver execution can change results. Repeated runs add workload and are not identical benchmark snapshots.
- Stop does not undo appointments or release offers from an earlier failed operation. Remaining scheduler reservations expire under the existing ten-minute rule. Use the run-scoped purge after the run reaches an eligible state.
- A preview is a snapshot, not realized savings. Its state is refreshed from the client's proposal each time the run is read. Later changes to any of its technician-days make a proposal unappliable.
- The runner progresses only from an open browser. It is not a background queue or throughput benchmark. Resume may temporarily conflict while an earlier bounded operation finishes. Resolve routing or database outages before retrying.

## Verification

`npm run test:booking-tests` covers radius defaults and presets, invalid radii, optional and deterministic seeds, deterministic batches and saved random state, radius bounds, round-robin fairness, real-address parsing, uniqueness and collision rejection, routability filtering, malformed Nominatim responses, weights, selection policies, horizon boundaries, and access gates. `npm run test:booking-tests:integration` refuses databases other than `waterflex_test` and requires seeded Omaha configuration plus the deterministic routing fixture and a Java scheduler that routes `metro-omaha` to it. Set `DATABASE_URL` and `SCHEDULER_TEST_URL` explicitly; the suite connects the default client to that scheduler for the run and revokes its token afterwards. It injects fixed fixture addresses because CI does not import Nominatim; production advancement always uses the validated local Nominatim path. It retains tagged test history in that disposable database for inspection.

Integration checks cover draft creation, persisted generation progress, repeated empty batches, pending-batch recovery, malformed generation journals, sequential order, duplicate creation and advances, all-or-nothing request creation, pause/resume/stop, concurrent callers, no-offer continuation, routing failures, confirmation conflicts, process interruption, lost confirmation and preview responses, unchanged promises and assignments before apply, whole-day proposals that include earlier bookings, exact-run purge, idempotent purge, survivors re-timed within their windows, and preservation of manual appointments, other runs, and proposal history. Browser coverage checks generation progress, history recovery, apply confirmation, conflict errors, applied-state refresh, read-only engine previews, purge confirmation, and purge state. Successful bookings must have a confirmed public-API hold for the run's client. Existing booking, optimizer/apply, and time-off checks also run in CI. The fixture accepts only fixed Monaco and Omaha sample/home coordinates; it is not a production routing fallback.

For real-road verification, start a small run against the local Omaha graph, inspect saved windows and proposals, reload the run, and open each day in Dispatch. Leave proposals unapplied unless explicitly testing manual approval.

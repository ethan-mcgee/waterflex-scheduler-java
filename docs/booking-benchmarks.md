# Booking benchmark protocol

`npm run benchmark:scheduling` extends the sequential booking workflow's seeded selection and scheduling client with isolated fleet datasets and concurrent request rounds. It measures search HTTP time including cancellation/acknowledgement, separately from subsequent customer selection. It does not include address entry, geocoding or browser transport. Do not label these samples browser-visible end-to-end latency.

Use a freshly migrated, unseeded `waterflex_test` schema whose name begins with `benchmark_`. The runner refuses an existing metro because overlapping service areas would make comparisons ambiguous. Each successful case is independently audited and recorded before deleting only that case's explicitly prefixed fixture rows. Failed cases remain for inspection. Output is JSONL with create-new semantics. It includes exact server revision and configuration-stage label, dataset hashes, seed, dates, hardware, every request outcome, served demand, incompletes, p50/p95/p99, assignment changes, retiming, and before/after independent workload, overtime, modeled cost, waiting and road/buffer metrics.

Launch the scheduler with `--spring.profiles.active=benchmark`, the dedicated JDBC schema and chosen routing provider. This installs only the read-only audit and cache experiment endpoints. Both reject databases other than `waterflex_test`; cache reset additionally requires a `benchmark_` schema. The audit independently validates confirmed routes and the common active-reservation arrangement, and rejects changes during measurement. Run cache experiments only on a dedicated idle benchmark instance. The runner resets scheduler memory/persistent road cache per case and optionally prewarms the pinned coordinate matrix. Routing-provider cache configuration and graph identity must also be recorded.

Required environment variables are `DATABASE_URL`, `ENGINE_URL`, `BENCHMARK_REVISION`, `BENCHMARK_VARIANT`, and a new `BENCHMARK_OUTPUT` path. Optional controls:

| Variable | Default |
| --- | --- |
| BENCHMARK_SIZES | 20,30,50 |
| BENCHMARK_WORKLOADS | SPARSE,CLUSTERED,DISPERSED,MIXED_SKILL,TIGHT_WINDOW,ABSENCE,NEAR_CAPACITY |
| BENCHMARK_CONCURRENCY | 1,5,10 |
| BENCHMARK_CACHES | cold,warm |
| BENCHMARK_REQUESTS | 30 per case; accepted range 10..200 |
| BENCHMARK_SEED | 17 |

Datasets preserve two-hour promises, existing buffers, dated home endpoints, skills and approved absences. The near-capacity fixture must independently measure at least 90 percent regular utilization before any requests. Sparse cases start empty. Confirmed appointments are deliberately co-located with each assigned technician to establish a feasible reproducible baseline; dispersed request pins span the known Omaha locations. These fixtures do not cover the full diversity of dispersed multi-stop routes and require complementary solver and real-road cases. Fleet size or low latency alone is not acceptance evidence.

Optional refinement after more than two regular insertion windows has a cooperative `booking.search.refinement-ms` budget, default 250 milliseconds and accepted range 0..1000. It reuses completed insertion candidates and demand totals. This limit does not apply to the prescribed scarcity neighborhood when regular choices number two or fewer. Routing requests remain governed by the original request deadline; the optional checkpoint is checked before routing batches and during scoring. Diagnostics record the configured limit and `REFINEMENT_TIME_LIMIT` when reached. Compare both throughput and fairness against the unrestricted revision, since reduced optional exploration can change solution quality.

Search responses additionally expose optional `measurements`: foreground JDBC execution count and nanoseconds (a batch counts once), locking-statement nanoseconds, sparse directed coordinate-pair counts, memory/persistent cache hits, pairs sent to shared routing resolution, and foreground thread CPU nanoseconds when supported. Locking-statement duration includes database execution and is an upper bound on lock wait, not a claim of separately measured contention. Shared resolution pairs are not provider HTTP calls: coalescing can serve multiple callers with one request. Independent routing workers, cancellation polling, database server CPU and transport are excluded from foreground counters. Stored offer diagnostics capture the point of publication; response measurements include the remainder of the commit. The benchmark records the complete returned search object, including queue time and these measurements, instead of converting unavailable observations to zero.

New benchmark artifacts also expose `/internal/benchmark/statistics`. The harness snapshots it after cache preparation and after search/selection, before the final independent audit. Subtract routing counters to obtain actual started leg, identity and geometry HTTP requests and requested directed pairs for the whole case, including shared workers. Failed requests still count as attempted calls. Process CPU includes scheduler background work. Heap-pool peak usage is reset at the case boundary and summed as a diagnostic upper bound, not simultaneous resident memory or a provider memory measurement. The response records rollout/search/solver configuration and maximum heap; audit responses include the actual policy rules and operating rates. Older artifacts return unavailable measurements. Never attribute the separate audit process's counters to the original server.

JDBC network timeouts are recalculated before statements and commit acknowledgement, in addition to PostgreSQL statement/lock timeouts. Expired cleanup can still attempt rollback with a one-millisecond network bound. Hikari restores connection network settings when returning connections to the pool. A transport failure can leave commit acknowledgement uncertain, so durable cancellation and unacknowledged-offer cleanup remain required. Browser User Timing entries named `waterflex.booking-api` separately record initial, pin, refresh and selection HTTP duration. Initial/pin entries explicitly include address validation and cannot be treated as isolated appointment-search time. Navigation aborts the in-flight browser request; the portal propagates cancellation to the scheduler.

Database admission reserves the configured pool-acquisition plus connection-validation bound before borrowing. A connection returned after the request budget expires is closed without executing work. Pool startup opens replacement connections in its worker, with a two-second PostgreSQL connect timeout; booking does not synchronously wait for first-connection establishment. Default acquisition and validation limits are each 250 milliseconds. Late requests can return retryable busy rather than entering a pool wait that cannot fit their remaining budget.

The harness records its own Git revision and SHA-256 hashes of tracked benchmark/client/schema sources and refuses modified tracked harness inputs. `BENCHMARK_REVISION` identifies the server artifact, not the harness. Set `BENCHMARK_ARTIFACT_SHA256` to the frozen jar's hash. Absent historical provenance remains explicitly unavailable.

Set `BENCHMARK_PORTAL_URL` to a local production-built portal using the same test schema and scheduler to measure browser HTTP latency. Headless Chromium sends the real `/api/book/refresh` request for each validated fixture job and records `performance.now()` through response-body parsing. This includes browser-to-portal transport and the portal's scheduler request and acknowledgement. It excludes address entry/geocoding and rendering. The browser version and measurement scope are recorded. Selection still uses the scheduler client and is measured separately. A six-second browser transport timeout classifies a failed measurement; it does not extend the scheduler's five-second budget. Do not mix these measurements with direct-client samples without identifying the transport.

Concurrent benchmark instances must fit the shared database connection budget. The first final real-road matrix was interrupted after 79 completed cases when additional idle test instances exhausted PostgreSQL's connection limit; its failed raw data is retained in `booking-omaha-interrupted-2026-09-24.*`. The restarted road matrix and reconstructed feature comparisons use four-connection scheduler pools, minimum idle one, and Prisma `connection_limit=4`. No production database setting was changed. Shared workstation and database interference remain explicit limitations of comparative timings.

For the exact original server, set `BENCHMARK_SERVER_MODE=legacy`, `BENCHMARK_LEGACY_JAR`, `BENCHMARK_JAVA`, `BENCHMARK_ROUTING_URL`, `BENCHMARK_AUDIT_URL` and `BENCHMARK_AUDIT_REVISION`. The audit service must use the same isolated schema and routing graph. The adapter verifies the original jar hash, starts a fresh hidden process on an unused local port for every case, and stops only that child. This resets original in-memory caches while retaining the cold/warm persistent-cache experiment. The unchanged original offers endpoint receives no invented deadline or completion metadata. Completion is recorded as null, not success or incomplete. Fully received HTTP errors remain failed attempts; uncertain transport failure stops the dedicated process and retains the case. The original measurement timeout is 120 seconds and is not a five-second service guarantee. Bounded diagnostic server logs are preserved beside the JSONL output.

Independent audits use the current canonical timing model for both implementations. Historical persisted timings and original operating behavior may differ; report this boundary when comparing modeled cost and paid waiting. Keep independent audit/background workers using one routing identity per schema. In particular, a fixture-routing worker and actual-road worker must not share time-off queues: a preview analyzed under one graph correctly fails apply under the other.

A variant label is provenance, not a feature toggle. Do not claim six-stage ablation coverage from differently labeled runs of the same binary. Original-baseline, insertion-only, snapshot/routing/evaluation, bounded-search, departure-timing and solver/CH comparisons need their actual controlled configurations. Full isolated stage coverage remains open.

`python infra/prepare-booking-ablation.py <stage> --revision <commit>` creates separate source trees under `.scratch`, exact reviewable patches, hashed manifests and a startup guard. Stages are `policy-insertion` (full directed matrix, whole-plan evaluation, early departure), `snapshot-insertion` (sparse routing and affected-route evaluation, early departure), and `bounded-early` (the same evaluation with bounded moves). Compare the last stage with the unmodified final artifact to isolate flexible departure. Use bounded search false for the first two and true for the last; reservations remain true throughout. The harness checks those settings and includes `BENCHMARK_ABLATION_MANIFEST` in provenance. Build each artifact with strict nullability and `-Dtest=AblationTimingTest,SchedulingPolicyTest,SearchDatabaseTelemetryTest,ReservationStateTest`; the timing test proves that independent validation and scoring both retain early waiting in the ablation. These intentionally altered artifacts are not expected to pass production tests that require flexible departure.

These are reconstructed feature comparisons, not historical release stages. Immutable snapshots, durable reservations, deadline propagation and independent validation remain shared safety infrastructure. The full-evaluation variant retains the same baseline calculation and fairness accounting; it disables affected-route aggregation for candidate metrics. The full-matrix variant uses the same directed routing provider and coordinate cache, materializing all identifier pairs instead of only needed pairs. Thus the comparison isolates sparse materialization and affected-route evaluation, not every infrastructure change from the original implementation. Benchmark artifacts refuse startup outside a local `waterflex_test` database with a `benchmark_` schema and the benchmark profile. Do not deploy them.

The corrected full-matrix stage materializes complete **per-route** matrices, matching the original insertion scope. An initial generator used all horizon identifiers together and exhausted its 768 MiB experimental JVM heap. That broader matrix was not representative of original insertion and is excluded from stage comparisons; its source, failed dataset and diagnostic evidence are retained. The correction changes only the matrix experiment, while the other frozen stage artifacts retain their recorded source revision.

Set `BENCHMARK_LOG_PATH` to the dedicated scheduler's log to archive validated preparation diagnostics after each measured case. Coverage, limits, candidates/moves, stop reasons and overtime decisions remain separate from API outcomes: preparation may precede a commit conflict, retries can produce multiple observations, and early queue/routing failures may have no preparation record. Missing observations are explicitly listed. The analyzer also reports observed-request counts for database/cache/queue/CPU totals, actual provider-call deltas and process/heap measurements without turning unavailable data into zero.

Completed experiments are archived under `docs/evidence/booking-*.json` with gzip source files. `infra/analyze-booking-benchmarks.mjs` requires every configured case, validates zero reported violations and preserves unknown legacy completion metadata. The structural-insertion comparison includes JFR profiling during parts of its first two variants; those samples diagnose hotspots and are not isolated performance estimates. Its final ten-request cold/warm variant ran without profiling. Final 30-request matrices are collected separately. Shared workstation activity, provider cache settings, graph identity and exact artifacts remain material limitations rather than implied production acceptance.
